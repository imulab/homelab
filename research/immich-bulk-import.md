# Immich bulk import (Apple library) briefing

> Resolves wayfinder ticket: best server-side path to import an existing Apple-ecosystem photo library (100-500 GB) into a verified Immich. Compiled 2026-08-19 via `/research` probe.
> Current at time of writing: **Immich v3.1.0** (server), **immich-go v0.32.0** (2026-06-25, the Immich v3-compat release), **@immich/cli 3.1.0** (versioned in lockstep with the server), **icloudpd 1.32.3**. All doc claims were read from docs.immich.app / immich-go repo docs on 2026-08-19.

## Recommendation (TL;DR)

**Blessed path: `osxphotos export` on a Mac with the full library, staged to a TrueNAS dataset, then `immich-go upload from-folder` into each user's own upload (non-external) library.**

1. On a Mac signed into iCloud Photos: let Photos download originals (or rely on `--download-missing`), then `osxphotos export` with `--download-missing --sidecar XMP --directory "{folder_album}"` so albums become directories and metadata rides in XMP sidecars.
2. Stage the export on a TrueNAS dataset (SMB/NFS), then run immich-go **v0.32.0+** (server-version aware, v3-ready) with `--dry-run` first, then for real with `--folder-as-album=PATH --pause-immich-jobs` and an **admin** API key.
3. Rely on immich-go's client-side hash check plus Immich's per-library checksum dedup for safe re-runs; use Immich's CLIP duplicates utility afterwards for edited-vs-original near-duplicates.

**Fallback: Apple's official takeout via privacy.apple.com + `immich-go upload from-icloud`** (the only path that rebuilds albums and capture dates from Apple's own CSVs without a Mac), or plain `@immich/cli upload --recursive --album` when immich-go misbehaves (it is the simpler tool and the docs' own recommendation for Google Takeout is immich-go, and vice versa immich-go is the community default; the official CLI is the low-risk dumb pipe).

**Top three fidelity risks** (detail below): (1) Favorites do not migrate, structurally, on any Apple route; (2) Live Photo HEIC+MOV pairing depends on Immich's metadata-extraction job reading Apple content identifiers, which is reliable for genuine Apple exports but has known failure modes; (3) capture dates on Apple-takeout files are wrong in the files themselves and must come from CSV/XMP metadata, and duplicate filenames (`IMG_1234`) are only weakly disambiguated.

## 1. Tooling

### immich-go (community, actively maintained, Immich v3-ready)

Single Go binary, no Node needed. Repo: [simulot/immich-go](https://github.com/simulot/immich-go); claims "Successfully handles 100,000+ photos" and "Compatible with Immich V2 and V3".

- **v3 compatibility:** v0.32.0 ("This release brings full compatibility with Immich V3.0.0") detects the server version and adapts API calls; deprecated `ReplaceAsset` was removed upstream, immich-go now uses copy semantics. Anything older than v0.32.0 must not be pointed at a v3 server.
- **Commands that matter here:** `upload from-folder` (arbitrary tree), `upload from-icloud` (Apple privacy.apple.com takeout; two-pass: scan `Photo Details*.csv` first, then apply dates + albums to each asset), `upload from-google-photos`, plus `from-immich` server-to-server. Note: `from-icloud` means an **Apple Data & Privacy takeout**, not an icloudpd download (confirmed in PR #822).
- **Dry-run:** `--dry-run` exists on all upload commands (confirmed in the from-folder man page and flag listings). Always run it first.
- **Re-run / duplicate behavior:** immich-go queries the server and "avoids re-uploading files that already exist"; the server itself dedups by checksum within the upload library. Re-running the same command is a no-op for identical bytes. This dedup is **per-library and upload-library only** (FAQ: "Duplicate checking only exists for upload libraries, using the file hash").
- **Useful flags:** `--folder-as-album=PATH` (mirror directory tree as albums), `--into-album`, `--date-from-name` (parse dates from filenames as last resort), `--manage-heic-jpeg` / `--manage-raw-jpeg` / `--manage-burst` (stacking policies), `--tag` / `--session-tag` / `--folder-as-tags`, `--on-errors=continue|skip|stop`, `--concurrent-tasks=16` default, `--ban-file` defaults (`.DS_Store`, `@eaDir/`, `Recently Deleted/`, ...).
- **Job interleaving:** `--pause-immich-jobs` pauses server queues during upload and resumes after (needs an **admin** API key; non-admin keys fail per issue #1060). Known gaps: it may not pause newer queues (OCR, duplicate detection, face recognition per issue #1247) and pauses maintenance queues indiscriminately (#1055). Community + Immich issues (#24937, discussion #27246) report missing thumbnails after large paused uploads; expect to kick thumbnail/metadata jobs manually after import.
- **Metadata priority** (doc-backed, upload-commands-overview): immich-go JSON sidecar, then **XMP sidecar**, then source-specific metadata (iCloud CSV, picasa.ini), then embedded EXIF/XMP, then filename date.
- **Rough edges:** issue #1121 ("from-folder discards all files", `reason=extension not included`, NAS import) is **open** with no maintainer response; workarounds are explicit `--include-extensions=.jpg,.jpeg,.png,.mp4,.heic` or per-type runs. Treat the first `--dry-run` as mandatory validation that files are actually seen.

### Official Immich CLI (`@immich/cli`)

Upload-only tool ("upload assets" and version check; "more features planned"). `npm i -g @immich/cli` (Node 20+; the old `immich` npm package is dead and 400s against v3 servers) or the `ghcr.io/immich-app/immich-cli` container with `IMMICH_INSTANCE_URL` / `IMMICH_API_KEY`.

- Hashes files client-side "to avoid uploading the same file multiple times"; `--skip-hash` is a pure speed trade; `--delete-duplicates` removes local files already on the server.
- Albums: `--album` (one album per top folder) or `--album-name`; `--recursive` needed for subfolders; `--concurrency` (default 4).
- **No** Live Photo pairing, no sidecar-driven favorites, no date repair, no pause-jobs. Docs themselves steer Google-Takeout users to immich-go.
- Immich docs confirm sidecar XMP files uploaded alongside media are ingested ("Selected metadata (title, description, date, rating, tags) is parsed from the sidecar and saved to the database"), but there are open bug reports about sidecar effects being lost after sidecar sync (issue #13897).

### Export routes from the Apple ecosystem, ranked by fidelity

| Route | Albums | Favorites | Capture dates | Live Photos | Edited photos | Pain |
|---|---|---|---|---|---|---|
| **osxphotos export** (Mac) | yes, as dirs via `--directory "{folder_album}"` | flag lost, exportable as an album | in EXIF + XMP sidecar | HEIC+MOV pair (Apple original) | `--skip-original-if-edited` (or keep both) | needs a Mac with full library; iCloud re-download is throttled |
| Photos.app "Export Unmodified Original" | no | no | in EXIF (+ optional IPTC XMP) | HEIC+MOV pair | originals only unless re-export edited | GUI selection, no scripting of albums |
| privacy.apple.com takeout → `from-icloud` | **yes, from CSV** | not documented | **only via CSV** (files' own dates are wrong) | both components, unpaired | originals | 3-7 days official, community reports up to weeks; flat `Photos/` dir with duplicate-name risk |
| icloudpd (v1.32.3) | no (per-album folder workaround) | no (open issue #789) | `--set-exif-datetime` writes EXIF | HEIC+MOV as separate files | originals (+ adjusted variant juggling) | project "looking for MAINTAINER"; requires "Access iCloud Data on the Web" and **ADP disabled** |
| iCloud.com download | no | no | in EXIF | stills typically; video component unreliable | option-click "unmodified original" | **1,000-item selection cap**, multi-zip failures |

Fidelity verdict: **osxphotos** is the highest-fidelity route because it is the only one with access to the Photos database (albums, folder structure, keywords, favorites-as-query) *and* the originals; the privacy.apple.com takeout is the only one that carries albums in a form immich-go natively rebuilds (`from-icloud`), but it is slow to obtain and has the weakest per-file disambiguation.

## 2. Fidelity concerns

**Live Photos.** Immich pairs HEIC + MOV server-side during the **metadata extraction job** by matching Apple's content identifier (`ContentIdentifier` EXIF on the still vs the matching tag in the MOV). Genuine Apple-sourced exports (Photos.app unmodified originals, osxphotos originals, icloudpd originals, Apple takeout) retain these identifiers, so pairing normally happens automatically once the job runs. Known failure modes: metadata extraction can silently complete without pairing (issue #24520), CLI uploads sometimes skip the video component (issue #21023, regression since v1.138-era), and old migrated libraries lose identifiers. Fallback: [immich-live-photo-linker](https://github.com/JacobBumgarner/immich-live-photo-linker) links by filename + timestamp via the API, with `--dry-run` and a revertable CSV audit log. Verification query after import: `SELECT count(*) FROM "asset" WHERE "livePhotoVideoId" IS NULL AND "originalFileName" ~ '\.heic$'` style (docs' database-queries guide has the live-photo query).

**HEIC vs JPEG.** Immich supports HEIC/HEIF natively (supported-formats doc); import originals as-is and let the server transcode for delivery. Do not pre-convert to JPEG: it burns quality, breaks Live Photo identifiers' pairing basis, and inflates size. The real HEIC/JPEG fork is *edited* photos: Photos edits are stored as instructions, and exporting "edited" yields a rendered JPEG plus (with osxphotos) optionally the original too. Decide once: `--skip-original-if-edited` (one asset per photo, edited wins) or export both and let Immich's duplicate/stack tooling reconcile. Note the HEIC+JPEG pairing policy exists on the immich-go side as `--manage-heic-jpeg`.

**Capture dates vs mtime.** EXIF `DateTimeOriginal` survives all original-preserving routes and Immich prefers it. The trap is the Apple takeout: exported files "often have incorrect file modification dates" (immich-go docs) and the real date lives only in the CSV, which is why `from-icloud` exists. icloudpd offers `--set-exif-datetime` to bake dates in during download. Immich also reads sidecar dates (priority chain starting `exif:SubSecDateTimeOriginal`). immich-go's `--date-from-name` is a last resort for metadata-less files. Never rely on file mtime: nothing in the Immich pipeline trusts it.

**What is importable vs structurally lost.**

- *Importable:* albums (via folder structure, or takeout CSVs), titles/descriptions/keywords/tags and GPS and rating (via XMP sidecars, doc-backed field list), capture dates, people (face recognition re-run server-side, not imported).
- *Structurally lost:* **favorites** on every Apple route. Immich favorites live only in its DB (discussion #20985: no XMP round-trip), immich-go sets favorites from Google Takeout JSON only, and Apple exports carry no favorite flag that anything downstream reads (icloudpd issue #789 is exactly this gap). Best available mitigation: in osxphotos, export favorites into a `Favorites/` directory (query `--favorite`) so at least membership survives as an album, and re-set the heart in Immich manually over time. Also lost: Memories (Apple's), shared-album participants, and edit history.

**Duplicates and re-runs.** Three layers: (1) immich-go / @immich-cli skip files whose checksum already exists in the target upload library, so re-running an interrupted import is cheap and safe; (2) the server rejects byte-identical uploads within the same upload library (byte-dedup is per-library, upload libraries only); (3) Immich's **duplicates utility** uses CLIP embeddings from the Smart Search job to group visually-similar assets (edited vs original, HEIC vs JPEG) with a "smart pick" of the best asset, always user-confirmed, never auto-deleted. Practical sequence used by the community: import, let smart-search run, then clean up with the duplicates utility.

## 3. Operational shape

**Duration.** Doc-backed anchor point: baty.net (Dec 2025) exported 47.5k photos via osxphotos in ~1h08m on a local library and uploaded to Immich with `immich upload --recursive --album` in ~3h over LAN, with facial recognition/OCR still churning afterwards. Scaling that to 100-500 GB: the **upload** phase is bounded by LAN throughput (at ~1 GbE saturation, 100 GB ≈ 2-3 h, 500 GB ≈ 12-14 h; immich-go's concurrent uploads and its network-folder glob optimization from v0.27 help when reading from NAS). The **dominant cost is usually upstream**: pulling a full-res library out of iCloud when "Optimize Storage" is on (Apple throttles; the osxphotos discussion #1883 pattern is the workaround, plan days for hundreds of GB). The **ML backlog** on CPU-only is the long tail: community consensus is ~1-5 s per image for CLIP plus face detection, so 100k+ assets is "several days to a week or more" on modest hardware; transcoding adds more for video-heavy libraries.

**Interleaving with ML jobs.** The FAQ is explicit that "the initial backup is the most intensive due to the number of jobs running"; hottest jobs are transcoding, Smart Search, Face Detection, then thumbnails (three thumbnail jobs per asset). Recommended shape: use immich-go `--pause-immich-jobs` with an admin key so the server ingests first (mind the coverage gaps in issue #1247), or manually pause queues in Administration → Jobs; keep ML/transcoding concurrency low (docs suggest 1, transcoding threads 1-2) while uploading; resume and let the backlog drain overnight after the upload finishes. Watch for the known "thumbnails missing after paused bulk upload" reports (#24937) and be ready to force-run thumbnail/metadata jobs. Do not run two big imports concurrently against CPU-only ML.

**User account vs external library.** Import **into each family member's own upload (default) library** via API. Reasons: checksum dedup only exists for upload libraries; albums, favorites, and tags via API all live per-user; quota accounting applies; and the external-library mechanism has different semantics (referenced in place, single owner set at creation and unchangeable, deletion semantics tied to mount ro/rw, metadata lost when files move). **Interplay with the planned external library for the other pre-existing tree:** keep the two strictly separate. External library for that tree (see `research/immich-storage-and-postgres.md` for the full external-library semantics); API import for the Apple libraries. Because duplicate checking is per-library and not global, a file present both in an external tree and uploaded via API will appear twice in the timeline with no dedup warning; if overlap is plausible, check with a CLIP duplicates pass after both are in. An external library is bound to exactly one user, so it cannot be used as a shared family import target anyway.

**Quota and disk pre-flight.**

- **Quota:** user quota (`quotaSizeInBytes`) makes the upload API **reject new uploads once exceeded**. If quotas are in use, verify `usage + incoming < quota` per user before starting; a mid-import quota failure leaves a partial import (recoverable via re-run, but annoying to diagnose).
- **Disk:** originals land under `UPLOAD_LOCATION/library`, plus thumbnails and transcodes. Doc-backed average overhead: thumbnails + transcodes add "roughly 10-20%" to library size; the staging `upload/` dir holds in-flight files. For a 500 GB import, have ≥ 650-700 GB free on the media dataset (video-heavy libraries can exceed the 10-20% average; community numbers in the storage briefing run higher). Note storage metrics only track free space at `UPLOAD_LOCATION`, so check `df` on every location actually used. DB growth is modest (1-3 GB typical, vector index scales with asset count).

## 4. Pre-flight checklist

Export side (per user, on their Mac):

1. Photos → Settings → iCloud: note whether "Optimize iPhone Storage" is on; if so plan for `--download-missing` (slow, throttled) or a pre-pass of "Download Originals to this Mac".
2. `osxphotos export /Volumes/staging/<user> --download-missing --sidecar XMP --touch-file --directory "{folder_album}" --skip-original-if-edited` (adjust the last flag per the edited-vs-original decision). Verify counts (`osxphotos` prints processed/exported/missing) and spot-check a Live Photo pair (`.HEIC` + `.MOV`) and one edited asset.
3. Optional: a second `--favorite --directory Favorites` pass if favorites membership should survive as an album.
4. Copy/rsync the staging tree to a TrueNAS dataset; do not import straight off a flaky SMB mount if avoidable (immich-go reads on NAS are fine, issue #1121's `--include-extensions` workaround noted).

Server side (TrueNAS, before import):

5. Confirm server v3.1.0 and install immich-go **v0.32.0+** (verify `immich-go version`; older builds break against v3 APIs).
6. Create an **admin** API key (needed for `--pause-immich-jobs`) scoped for the import, revocable afterwards.
7. Disk headroom check on all Immich locations: originals ≥ 1.0x, thumbs+transcodes ≥ 1.2x of incoming size, plus upload staging room. Quota check per target user (`usage + incoming < quota`, or quota unlimited).
8. Decide storage template now (template changes only apply to new assets; migrating later means a storage-migration job).
9. In Administration → Jobs: note current queue state; plan to pause (or let `--pause-immich-jobs` do it) during upload, and lower ML/transcoding concurrency to 1 for the drain phase.
10. Run `immich-go upload from-folder --server ... --api-key ... --dry-run --folder-as-album=PATH /dataset/staging/<user>` and confirm the file count matches the export count (catches #1121-style extension filtering surprises).
11. Real run: same command without `--dry-run`, plus `--pause-immich-jobs --on-errors=continue --log-file import-<user>.log --session-tag import-2026-08`. Re-runs after interruption are safe (checksum dedup).
12. After import: force-run metadata extraction + thumbnail jobs if paused; sanity-query unpaired Live Photos; run Smart Search, then Face Detection, then the duplicates utility; finally re-heart favorites from the `Favorites` album.
13. Keep the staging tree until the Immich library is backed up; only then delete from iCloud (Recently Deleted keeps 30 days).

## Confidence notes

- **Doc-backed:** immich-go v0.32.0 v3 compatibility and server-version detection; `--dry-run`, `--pause-immich-jobs`, `--folder-as-album`, `--date-from-name`, banned-file defaults, duplicate-skip behavior, XMP-sidecar metadata priority; `from-icloud` input format (flat `Photos/` + `Photo Details*.csv`, two-pass date/album application) and its takeout provenance (privacy.apple.com); official CLI flags (`--album`, hashing, `--skip-hash`, `--delete-duplicates`); Immich XMP sidecar field list (title/description/date/rating/tags/GPS, favorites absent); per-library upload-only checksum dedup; external library semantics (single owner, referenced in place, ro-mount behavior, deletion-on-rescan); duplicates utility is CLIP-based and user-confirmed; FAQ guidance on initial-import job pressure and concurrency; quota model (`quotaSizeInBytes`, uploads rejected at quota); Photos.app "Export Unmodified Original" exports HEIC+MOV pairs with optional IPTC XMP (Apple support doc); iCloud.com 1,000-item selection cap (Apple support doc); icloudpd v1.32.3 features (live photo as separate files, `--set-exif-datetime`, ADP/web-access requirements, maintainer search notice).
- **Community-sourced:** osxphotos as the de-facto Apple→Immich route and its flag choices (`--download-missing`, `--directory "{folder_album}"`, `--skip-original-if-edited`), including the baty.net timing anchors (47.5k photos, ~1h export + ~3h upload); CPU-only ML backlog "days to a week+" for 100k+ assets; `--pause-immich-jobs` needing an admin key (#1060) and its queue-coverage gaps (#1247, #1055); missing thumbnails after paused bulk uploads (#24937, #27246); Live Photo pairing being reliable for Apple-native originals but with recurring failure reports (#24520, #21023) and the linker-script workaround; iCloud.com live-photo video components being unreliable in web downloads; duplicate-name weakness in `from-icloud` album matching (flagged by simulot in PR #822, unresolved in thread); immich-go #1121 (from-folder discarding files) open with workarounds.
- **Undetermined from public sources:** whether Apple's `Photo Details` CSV carries a favorite flag at all (nothing found either way; treat favorites as lost regardless, since no importer maps it); exact 2026-current behavior of iCloud.com Live Photo downloads (mixed reports); immich-go container image support details (binaries and Homebrew are documented; container use not verified this session); whether `--pause-immich-jobs` coverage gaps (#1247) are fixed in v0.32.0.
